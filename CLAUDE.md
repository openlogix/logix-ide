# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The AI spec is the source

The **AI spec** is this file plus any files it points to (e.g. `.claude/` files added later). It is the real source of the repo. A capable AI agent should be able to regenerate everything else from it, with equivalent behavior: the app, tests, GitHub workflows and actions, scripts, packaging config and docs.

- **Detailed enough, not too detailed.** Record what and why: requirements, decisions with their reasons, contracts between parts (commands and events, file formats, names, paths, pinned versions), verified facts about external tools (Apio, Tauri, GitHub), conventions, and the non-obvious lessons (workarounds, "why not X"). Leave out what follows from these or from standard docs, such as line-by-line code. Test: if an agent regenerating the repo would likely get it wrong without a sentence, keep the sentence; otherwise leave it out.
- **Same commit.** Every change to behavior, workflows, scripts or decisions updates the AI spec in the same commit. Remove what no longer holds.
- **No personal info.** Nothing that identifies or locates a person: no names, emails, machine-specific paths, account details or private notes. Use placeholders (e.g. `/Users/you`).
- **Pull requests are rules or prompts.** Ideally a pull request changes the AI spec (a requirement, rule or decision with its reason), or gives the prompt to run, rather than hand-written code; the code is then generated from it. A pull request that does include code must also include the AI spec change that explains it, since code the AI spec doesn't account for would be lost when the repo is regenerated. Its description gives the prompt(s) used. When working on a code-only contribution, first turn it into the rule it implies and add that to the AI spec.

## Project goal

**Name: Logix IDE.** The product is "Logix IDE", as on its product page (www.openlogix.org/ide/) and in the Open Logix family (Logix Engine, Logix CLI, ...). Use the full name wherever the product is named as such: the app and bundle name (`productName`, so `Logix IDE.app`), window title, About box, the macOS app menu (About/Quit Logix IDE), installer text, page titles (README, docs site name, docs home and Installing), and release notes. In running text "Logix" is fine as the short name, as the product page does. Internal names stay lowercase `logix` and don't change with the product name: `~/.logix/`, `logix.json`, `logix.log`, the `logix-darwin-arm64-*.dmg` file name, the `logix` npm/Cargo package, the bundle identifier, and the default projects folder `~/Documents/Logix` (renaming them would break existing installs and projects).

**Motto: "The Arduino experience, for FPGAs."** Use it, in quotes, wherever Logix describes itself: the docs (site description and home page), the About box, the release notes, package descriptions, and any new place like that (e.g. a README or app store text).

**Mentioning Arduino**: Logix mentions Arduino only to describe how it feels (the motto, "as in the Arduino IDE"). Don't use "Arduino" as a name for anything of Logix's, or Arduino's logo or artwork. Keep the notice "Logix is not affiliated with or endorsed by Arduino. Arduino is a trademark of Arduino SA." where Logix presents itself: README (Trademarks), the docs footer (`copyright` in `mkdocs.yml`) and the About box (`menu.rs`).

A minimalist, Arduino-IDE-like desktop IDE for FPGAs. Users write **Verilog** (instead of C/C++), and the IDE uses **[Apio](https://github.com/FPGAwars/apio)** as its backend toolchain (instead of gcc / arduino-cli).

### Requirements

- **Look and feel similar to the Arduino IDE**: a simple editor with a small set of obvious actions (e.g. verify/build, upload), a board selector, an examples menu, and an output console. Keep it minimal; ease of use for beginners comes before power-user features.
- **Easy to install and use** on three platforms, all of them first-class:
  - Linux x86-64
  - Windows x86-64
  - macOS ARM (Apple Silicon)
- **The installer is the only thing users need.** No manual installation of prerequisites (no Python, Node, Rust, runtimes, Homebrew, package managers, or a separately installed Apio). Everything else either ships inside the installer or is fetched automatically by the IDE at runtime with progress shown (the Apio bundle and Apio's packages; see Design notes). Implications:
  - The released app must not depend on anything from the developer machine (dev tools, Homebrew libraries, `PATH` entries). It must never use an `apio` found on the user's `PATH`; it uses only the bundle it downloaded. (An explicit developer-only override pointing at a local Apio, e.g. for testing `apio api` changes, is fine as long as it's off by default.)
  - Windows: the installer must handle the WebView2 runtime itself (Tauri's bundled bootstrapper or offline installer), not ask the user to install it.
  - Linux: prefer formats that work out of the box (AppImage); `.deb` dependencies must resolve automatically through the package manager.
  - Board USB drivers / permissions (Windows drivers, Linux udev rules) are set up from inside the IDE with guided steps, using Apio's driver support where it exists, not as a manual pre-install step.
- **Apio boards**: users choose a target board from the boards Apio supports.
- **Apio examples**: users can browse and open the examples Apio ships, as the Arduino IDE does with its examples. **Decided for the move to Logix Engine:** the IDE then keeps its own project model and its own examples in that model, with no Apio (the engine has no project model or examples; see the website repo's `CLAUDE.md`). Until the move, Apio's examples stay. **Decided for step 4** (with reasons): examples stay per board, like Apio's (a folder per board per example), starting from Apio's examples for the engine's boards, relicensed to Apache-2.0 (the user confirmed the right to do so); they're bundled in the app (in this repo, shipped in the installer, like Arduino's built-in examples: offline and always matching the IDE). The project model keeps `main.v`/`main.sv` with top module `main` (one fixed rule, nothing to configure) and flat folders (tabs are top-level files; testbenches stay `*_tb.v`/`*_tb.sv`). Since the engine builds only the files Logix lists, the build copy no longer needs to leave out Verilog/pin files in subfolders (only nested projects), so the "Not used in the build" note goes.
- **Core workflow (initial scope)**: edit Verilog → synthesize (`apio build`) → program the board (`apio upload`).
- **Testbenches**: write testbenches, run them (Run Tests) and view their signals in GTKWave (Simulate); see Run Tests / Simulate.

### Platform rollout

Development starts on **macOS ARM**, and that is the only platform implemented, built and tested at first. Windows x86-64 and Linux x86-64 come later and must be addable without restructuring:

- Keep platform-specific code (Apio bundle selection/URL, data directories, executable permissions, macOS quarantine handling, serial port naming, packaging) behind small per-platform functions or modules, selected in one place. Don't scatter OS checks through the code.
- Use cross-platform APIs for paths and processes (no hardcoded `/` separators, shell-specific commands or macOS-only paths in shared code).
- Where a Windows or Linux branch isn't implemented yet, make it fail clearly ("not supported yet") rather than silently doing the macOS thing.
- CI and release start with macos-arm64 only. The other build-matrix entries are added when those platforms are implemented.

### Design notes

- The IDE is a front end. Synthesis, place-and-route, programming, simulation and the board/example catalogs all come from Apio. Call the Apio CLI, preferring `apio api ...` JSON over parsing human-readable output. Don't reimplement toolchain logic or hardcode board/example lists that Apio already provides.
- **Users should not need to learn Apio**, just as Arduino users don't need to learn gcc. Don't expose Apio concepts, files or commands in the UI unless there's no way around it.
- **Project on disk** (decided): a project is a folder with any name (spaces OK). The main file is `main.v` (or `main.sv` for SystemVerilog) with top module `main`, the same convention Apio's examples use. It's always the first tab and can't be renamed or deleted; new projects get `main.v`. Top-level source files (`.v .sv .vh .svh` and the pin constraint formats `.pcf .lpf .cst .xdc .pdc .ccf`) appear as editor tabs, with `main.v` first. Anything else in the folder (subfolders, docs) is kept as is. Save As refuses a location inside a Logix project (the current one or any folder with a `logix.json` above it: `project::enclosing_project`), since a nested project would be copied into its own builds (and, inside the source, into itself). File names can't contain spaces or path separators; the rules live in `project::check_new_file_name`. Creating, renaming and deleting files are held in memory and applied on save, like text edits, so "Don't Save" leaves the folder untouched. `logix.json` stores IDE settings (currently the board) and preserves unknown fields. New projects default to `~/Documents/Logix/`. Code: `src-tauri/src/project.rs`.
- **Simple project model**: the user's project (the "sketch") is the IDE's own simple model, not a full Apio project. It doesn't need to contain an `apio.ini`. At build/upload/sim/test time, the IDE copies the user's sources (unsaved edits included) into a build folder, runs Logix Engine on it with the board and top module, and shows the results mapped back to the user's files (e.g. error line numbers).
- **Apio integration**: prefer working with stock Apio as is. If embedding needs something Apio doesn't offer (e.g. machine-readable board/example lists, structured diagnostics, building without a user-visible project), Apio can be extended, preferably through its `apio api ...` command family, which is meant for programmatic use. Keep those extensions general and suitable for upstreaming, not specific to this IDE.
- **Asking for Apio changes is welcome.** When an Apio change or new feature would make integration with host applications like Logix simpler or more robust (e.g. machine-readable progress, offline-friendly commands, structured errors), propose it instead of working around Apio in the IDE. Describe what's needed and why, and point out a temporary workaround if the IDE needs one until the change ships.
- Apio's CLI syntax has changed between major versions. Check `apio --help` / `apio <cmd> --help` for the version in use rather than assuming command syntax.
- **Apio is not part of the installer.** The IDE installer contains only the IDE. Delivery happens in two stages, the same way the Apio VS Code extension works:
  1. The IDE downloads the platform-specific standalone Apio bundle at runtime (first launch, or when a newer pinned version is required) into a per-user data directory, and runs Apio from there.
  2. Apio then downloads its own toolchain packages automatically. The IDE doesn't manage those packages itself; it only shows Apio's progress and errors to the user.
  
  Both downloads must show clear progress, be retryable (a Retry button re-runs setup; downloads don't resume), and fail with a plain-language message (e.g. no network). The Apio version the IDE expects is pinned in one place: `package.json` `appConstants.apioCliReleaseRepo` / `apioCliReleaseTag` (the same keys as the Apio VS Code extension). `src-tauri/build.rs` reads and checks them and passes them to the Rust code (`apio::APIO_RELEASE_REPO` / `APIO_RELEASE_TAG` via `env!`); a test checks they match.
- **Logix Engine delivery (move from Apio, steps 1 to 3 of 4 done)**: the IDE also downloads the pinned engine release and starts it at startup, after Apio's setup. The board list, Verify, Upload, Run Tests, Simulate, Show Diagram, Auto Format, the USB devices and the connected boards use the engine, and so does the language server's executable (`engine::program_path`); only the examples still come from Apio until step 4. Pinned in `package.json` `appConstants.engineReleaseRepo` / `engineReleaseTag` (`openlogix/logix-engine`), checked by `build.rs` and passed in as `engine::ENGINE_RELEASE_REPO` / `ENGINE_RELEASE_TAG`; a test checks they match. The package is `https://github.com/<repo>/releases/download/<tag>/logix-engine-<platform>-<yyyymmdd>.tgz` (engine platform ids `darwin-arm64`, `linux-x86-64`, `windows-x86-64`), with one top-level `logix-engine/` folder holding the `logix-engine` executable and `LICENSE`. The IDE launches it as `logix-engine --engine-folder ~/.logix/engine` and talks MCP over stdin/stdout (crate `rmcp`, the client side of what the engine uses, over the child's pipes as an async reader/writer pair; see the engine adapter for why); the engine's stderr goes to the IDE's stderr and it writes its own log in `~/.logix/engine/logs/`. Setup calls `get_engine_info` (logs the engine version and log file) and, if a package isn't `installed`, `install_packages` with a progress token: the engine reports one phase per package ("Installing oss-cad-suite") on a scale of 100 per phase, so the phase's percentage is progress modulo 100. Once installed, startup is offline-safe (`get_engine_info` is local). The engine's packages (about 650 MB) are a second download next to Apio's until Apio is removed. The engine's rules that matter to the IDE: its folder's last name must contain "engine", and build folders need "build" in one of their last two names.
- Cross-platform behavior matters a lot: watch path handling (spaces, non-ASCII, Windows drive letters), per-user data directories, executable permissions on downloaded files, macOS quarantine of downloaded binaries, and serial/USB permissions on each OS.

### Apio facts (verified with Apio 1.7.0, release `2026-10-22`)

- **Bundle download**: `https://github.com/fpgawars/apio/releases/download/<tag>/apio-cli-<apio-platform>-<yyyymmdd>-bundle.<ext>`. Apio platform ids are `darwin-arm64`, `linux-x86-64` and `windows-amd64`; ext is `tgz`, or `zip` on Windows. The archive has one top-level `apio/` dir containing the `apio` executable and `_internal/`. Releases come out daily as pre-releases; pin a non-pre-release tag. (This mirrors the Apio VS Code extension's `downloader.js`.)
- **`APIO_HOME` must be printable ASCII with no spaces**, or Apio exits with an error. That's why the IDE's data lives in `~/.logix/`, not `~/Library/Application Support/`. Project directories *may* contain spaces.
- **Packages**: any Apio command auto-installs missing packages. `apio packages install` does it explicitly. On macOS they're about 650 MB to download and about 3 GB on disk (oss-cad-suite, openxc7, verible, definitions). When stdout isn't a terminal, the progress bars only print when each package finishes.
- **`apio api ...`** (get-boards, get-examples, get-system, get-packages, get-project, get-build-report, scan-devices, ...) produces JSON. Status lines can be mixed into stdout, so always use `-o <file>` (plus `-f` to overwrite) and read the file instead of parsing stdout.
- **Colors**: Apio prints through Rich, which only colors terminal output. `Apio::command()` sets `FORCE_COLOR=1`, `TERM=xterm-256color` and `COLUMNS=120` (and removes `NO_COLOR`), so output is colored and wraps less. Parsers must use `process::strip_ansi` first; the console converts the codes to colors with `ui/src/lib/ansi.ts`. Tool output (yosys, nextpnr, iverilog) isn't colored.
- **IDE data layout** (`~/.logix/apio/`): `bundle/` is the unpacked Apio, plus `download-metadata.json` recording its source URL (a different pinned URL triggers a re-download). `home/` is the IDE's private `APIO_HOME` (packages), separate from the user's own `~/.apio`. `tmp/` holds downloads and unpacking.
- **Offline startup**: `apio packages install` always needs a fresh online config, so it fails offline even when everything is installed. Setup uses `apio api get-system -o <file> -f` instead: it installs missing packages but falls back to the cached config offline. Offline with a package missing, or with no cached config, is still a hard failure (expected). Proper fix requested in [apio#1185](https://github.com/FPGAwars/apio/issues/1185) (`apio packages install --cached-ok`).
- **Pending Apio requests** that would simplify the IDE once they ship: [apio#1184](https://github.com/FPGAwars/apio/issues/1184) (real-time JSON Lines event stream via `APIO_EVENTS_FILE`, for progress and later diagnostics) and [apio#1185](https://github.com/FPGAwars/apio/issues/1185) (above).

### Where builds happen

- **Release builds (installers, signing, notarization) are made only by the GitHub Actions build workflow**, never on a developer machine. Signing secrets live only in GitHub secrets.
- **Pre-releases**: `.github/workflows/build-pre-release.yaml` (on every push to `main`, daily at 00:00 UTC, and manual; `concurrency` cancels a running build when a newer one starts) uses the shared Open Logix actions from the `openlogix/.github` repo, as `openlogix/.github/actions/<name>@v1` (e.g. `get-release-and-package-tags`, `ensure-no-conflicting-release`, `cleanup-old-prereleases`, `scan-files-for-viruses`, `create-pre-release`, and JSON helpers such as `set-env-from-json`). That repo owns, documents and tests them; change them there, not here. They need no checkout. It runs `prepare` (tags `yyyy-mm-dd` / `yyyymmdd`, `BUILD-INFO.json`), then one `build-<platform>.yaml` per platform (only `build-darwin-arm64.yaml` for now; add Linux and Windows the same way), then `pre-release`. That last job scans for viruses, writes the release notes, keeps the 5 newest pre-releases, replaces an existing pre-release with the same tag (a stable one fails the run), and publishes.
- **macOS package**: a `.dmg` (drag Logix IDE to Applications), named `logix-darwin-arm64-<yyyymmdd>.dmg`. The build job runs `scripts/test.sh`, then `npm run tauri -- build --bundles dmg`, and checks the signature. The .dmg window (Logix IDE on the left, Applications on the right, 128 px icons, and a background with an arrow and "Install Logix IDE" and "Drag the Logix IDE icon onto the Applications folder.") is set in `bundle.macOS.dmg`. The background `src-tauri/icons/dmg-background.tiff` (1x and 2x) is drawn by `swift src-tauri/icons/make-dmg-background.swift src-tauri/icons/dmg-background.tiff`, whose positions must match that config; Tauri only applies it in CI because the step sets `TAURI_BUNDLER_DMG_IGNORE_CI=true`. The app is **ad-hoc signed** (`bundle.macOS.signingIdentity: "-"` in `tauri.conf.json`), since Apple Silicon requires a signature and the verify step checks for it. It isn't notarized, so the release notes tell users to clear the quarantine flag from the downloaded `.dmg` before opening it (`xattr -c ~/Downloads/logix-darwin-arm64-<yyyymmdd>.dmg`); the app dragged out of it is then not quarantined either.
- **The developer machine does only the minimal edit/run/debug cycle**: the dev server (`tauri dev`), unit tests, and lint/type checks. Don't add local scripts that produce installers, and don't make local development depend on signing setup.

## Architecture rules (keep the stack replaceable)

- **Thin IDE backend**: toolchain knowledge belongs in Apio (extended via `apio api ...` if needed), not in the Rust layer.
- **One UI↔backend interface**: all UI-to-backend calls go through a single, documented set of Tauri commands and events (e.g. list boards, list/open examples, build, upload, stream output, report diagnostics, Apio download status). The UI must not run processes or touch the file system directly.
- **One Apio adapter**: every Apio invocation and every bit of Apio output parsing lives in one module, so an Apio upgrade or CLI change touches one place.
- **Primary Apio commands are shown in the console; info commands aren't.** Primary commands (now only `examples fetch`) go through `Apio::run` (in `src-tauri/src/apio/mod.rs`), which logs the command line (dimmed, `$ apio ...`) and streams the output. Info commands (`apio api ...`) go through `Apio::run_silent`, which shows nothing and puts Apio's output in the error if it fails. The one exception is `apio api get-system` during setup, which uses `run_output_only`: no command line, but its output stays because on the first run it's the progress of installing the FPGA tools. Tasks (`TaskEvent`s) and setup send lines through their own Tauri `Channel`; other commands (fetching an example, Auto Format's engine output) use `console_log` in `commands.rs` (`apio-output` events). `Apio::command()` is private, so nothing can bypass these.
- **Framework-free core logic**: temporary project generation and diagnostic mapping are plain code with unit tests and no dependency on Tauri or Svelte.
- **Behavior-level end-to-end tests**, in two halves, since Playwright can't drive the Tauri window on macOS (Tauri's WebDriver tool only supports Windows and Linux):
  - **UI**: `ui/e2e/*.e2e.ts` run the real UI in Playwright's WebKit (the engine behind the macOS window). `vite --mode e2e` (port 1430) replaces `ui/src/lib/backend.ts` with `ui/e2e/fakeBackend.ts`, which is typed against the real backend, so a changed backend API fails `npm run check` until the fake is updated. It uses the engine's real boards, Apio's real examples, and replays real engine output for Verify and Apio output for the rest (`ui/e2e/fixtures/`); Verify and Upload also send a phase (`progress` events), and Upload's "Writing flash 42%"; a build fails if `main.v` contains "oops" or blinky's `;` after `assign led = counter[23]` is missing; tests trigger native-menu actions with `window.__fake.menu(id)`.
  - **Backend**: unit tests cover the engine adapter's parts (notification routing, result and error mapping, console); the `#[ignore]`d `real_engine_build` runs every task but Simulate against a real engine (see Tests). `capture_fixtures` recaptures the fake backend's fixtures from a real engine.

## Source layout

- Top level (kept short for GitHub): `ui/` (the web UI project: `src/`, `e2e/`, `index.html`, `vite.config.ts`, `svelte.config.js`, `tsconfig.json`, the Playwright configs; builds to `ui/dist/`), `src-tauri/` (the Rust backend; Tauri's standard name), `scripts/` (`run.sh`, `test.sh`, `clean.sh`; they `cd` to the repo root), `docs/` + `mkdocs.yml`, and `package.json` / `package-lock.json`, which stay at the root because npm and the Tauri CLI run there. The npm scripts point Vite, Vitest, svelte-check and Playwright at the configs in `ui/` (Vite's `root` is `ui/`; Playwright's web server runs from the repo root, and test paths like `docs/images` are relative to it).

- `ui/src/`: Svelte 5 UI (runes syntax: `$state`, `$props`, etc.). Entry `main.ts` mounts `App.svelte`. Theme colors are CSS variables in `app.css`, with a dark-mode override.
- `ui/src/lib/backend.ts`: the UI↔backend interface. Every Tauri command used by the UI has a typed wrapper here; components never call `invoke` directly.
- `ui/src/lib/format.ts`: pure UI helpers (byte formatting, progress, capped console buffer), unit-tested in `*.test.ts` next to them.
- `src-tauri/src/commands.rs`: the Tauri commands (the backend side of that interface). New commands must also be registered in `lib.rs` (`generate_handler!`) and wrapped in `backend.ts`. Command structs use `#[serde(rename_all = "camelCase")]` to match TypeScript.
- Long-running commands stream progress to the UI with a Tauri `Channel` passed as a command argument (see `setup_apio` and `backend.setupApio`). Shared backend state is `AppState` in `lib.rs`.
- `src-tauri/src/platform.rs`: the only place that identifies the OS/CPU (`Platform` enum, `is_implemented()`). Apio platform ids, bundle ext, exe name, data dir and post-unpack fixups live here.
- `src-tauri/src/apio/`: the Apio adapter, the only code that runs Apio or knows its layout. `mod.rs` has the pinned release (`APIO_RELEASE_TAG`, from `package.json`), `Apio::command()` (every Apio invocation starts here; it sets `APIO_HOME`) and the data layout. `bundle.rs` downloads and installs the bundle. `process.rs` runs Apio and streams output lines. `setup.rs` runs the startup flow (bundle, then `apio api get-system`, which installs missing packages; see "Offline startup") and emits `SetupEvent`s.
- `src-tauri/src/engine/`: the Logix Engine adapter, the only code that runs the engine or knows its layout. `mod.rs` has the pinned release and the data layout, `bundle.rs` downloads and installs the engine package, `client.rs` is the MCP session (`Engine::start`; `Engine::call` with optional progress, `call_with` also with live output and cancellation; a tool's error object comes back as `Err(value)`, not as a failed call). **rmcp handles each notification on its own spawned task**, so their order isn't kept and a call's result can arrive before its last notifications (lost console lines). So the IDE spawns the engine itself and its stdout goes through `tee`, which routes progress (by progress token) and `logix/output` (by `request_id`) synchronously, in order, before passing each line on to rmcp (`().serve((duplex, stdin))`); by the time a call has its result, it has had everything sent before it. **rmcp gives every request its own progress token and replaces any token the caller sets**, so `call` sends with `send_cancellable_request` and registers by the handle's `progress_token` and `id`; notifications that arrive before the call registers are kept and replayed in order (`Routes<K, T>`). `logix/output` is asked for with `_meta` `{"logix/output": true}` (`PeerRequestOptions.meta`). Cancel: `call_with` waits on `handle.rx` or the `CancellationToken`, then `handle.cancel()` sends `notifications/cancelled`; the engine stops its tools and, as MCP requires, never answers, so the call returns `{"category": "cancelled"}` itself. `catalog.rs` reads the boards and their USB filters (`get_catalog` with boards and FPGAs, `arch` from the FPGA's `architecture`), `task.rs` runs the tasks (`Runner`: Verify, Upload, Run Tests, Simulate, Show Diagram), `format.rs` Auto Format, `devices.rs` the USB devices and connected boards, `setup.rs` the startup flow; `phase_sink` (`mod.rs`) follows the engine's phases. The result types both adapters return (`Task`, `TaskOutcome`, `TaskEvent`, `Diagnostic`, `BuildReport`, `dedup`) are in `src-tauri/src/outcome.rs`. `src-tauri/src/download.rs` (download with progress, `.tgz` unpacking) is shared by both adapters, and so are the setup events (`src-tauri/src/setup_events.rs`).
- `ui/src/lib/Editor.svelte`: the CodeMirror editor. It keeps one `EditorState` per file (`reset`, `show`, `add`, `rename`, `remove`), so each tab keeps its own undo history. Edits are reported through `onChange(file, text)`.
- `ui/src/lib/workingProject.ts`: the in-memory project the UI edits (files with saved/current text, removed files, structure changes) and the unsaved-changes logic. Pure functions, unit-tested.
- `src-tauri/src/project.rs`: the project model on disk (load, save with removed files, Save As with copying of other contents, file name rules). Plain Rust with tests, no Tauri. It validates every name the UI sends, so a bad name can't write outside the project folder.
- `src-tauri/src/apio/catalog.rs`: boards and examples from `apio api get-boards` / `get-examples` (parsed into `Board` and `Example`), and `fetch_example` (`apio examples fetch <board>/<name> -d <tmp>/example`; Apio requires that the destination doesn't exist). The lists are cached in `AppState.catalog` for the run. Board and example ids are checked before being passed to Apio.
- **Unsupported examples are hidden** (`example_is_supported`): Logix only lists examples with a top-level `main.v`/`main.sv`, no subfolders, and an `apio.ini` with one env for the example's board, `top-module = main`, and only `board`/`top-module`/`default-testbench`. Anything else (multiple envs, `defines`, `constraint-file`, `programmer-cmd`, extra tool options) would build differently in Logix. Apio's example list has no such details, so the check reads `<apio-packages-dir>/definitions/examples` (from `apio api get-system`). With Apio `2026-10-22`, 146 examples pass this check and 18 don't. Examples for boards the engine doesn't support are hidden too (`catalog` in `commands.rs`), which leaves 108 shown and 56 hidden. Re-check after Apio updates with `LOGIX_EXAMPLES_DIR=<dir> cargo test survey_real_examples -- --ignored --nocapture`.
- **Bare Minimum** (as Arduino's File > Examples > 01.Basics > BareMinimum): the first entry of every board in the Examples dialog (`BARE_MINIMUM` in `ui/src/lib/examples.ts`; boards without examples are listed for it). `open_bare_minimum` fetches the board's starter example and `src-tauri/src/bare.rs` keeps only its pin file plus a `main.v` with the starter's ports and `assign <output> = 0;`. Why not an empty `main` with the pin file: Apio's example pin files list only the pins that example uses, iCE40 rejects a port without a pin (`--pcf-allow-unconstrained`), and an empty design fails with "Failed to autodetect top module". A board without a starter gets `bare::NO_PINS_MAIN` (placeholder ports and a note to add a pin file); `new_project` uses it too for those boards. Check against Apio's examples with `LOGIX_EXAMPLES_DIR=<dir> [LOGIX_BARE_OUT=<dir>] cargo test survey_bare_minimum -- --ignored --nocapture` (with Apio `2026-10-22`: all 98 starters read, and built).
- **Opening an example** gives an unsaved project (`dir: null`) with `templateDir` set to the fetched folder and the board set. The first save asks for a location and copies the example's other files (e.g. `main_tb.gtkw`) from `templateDir`; Apio's `apio.ini` and hidden files are skipped. UI: `ui/src/lib/ExamplesDialog.svelte`, with search and grouping in `ui/src/lib/examples.ts`.
- **Verify / Upload** (toolbar, Cmd+R / Cmd+U, Project menu): `run_task` builds from the project's **in-memory** files (unsaved edits included) in `~/.logix/build/`. `src-tauri/src/build_dir.rs` (plain Rust, tested) fills that folder with the files and the other contents of the project folder (or example template); no `apio.ini`. Logix only builds top-level files (and Apio, which still provides the examples, reads Verilog and pin files from all subfolders), so the copy (`CopyMode::Build`) leaves out Verilog/pin files in subfolders and whole nested projects (folders with a `logix.json`); data files still go along, and the output pane says what was left out ("Not used in the build: …"). The folder is reused for the same project (key = project folder) so `_build/` (the engine's `_build/logix/`) speeds up repeated builds; another project starts from an empty folder. Every task runs on the engine (`engine::run_task`, `engine/task.rs`) with that folder as `source_folder`, `_build/logix` as `build_folder` (it needs "build" in one of its last two names), top module `main`, the project's `.v`/`.sv` files minus testbenches as `source_files` (include files are found by the engine), and the first pin file as `constraint_file` (none: the error `NO_CONSTRAINT_FILE`, explained by `friendly`). A board that isn't in the engine's catalog is refused with a plain message before anything runs. Only one task runs at a time (`AppState.task`).
- **Verify = lint + build**: for `Task::Build`, the engine's `lint` runs first (unless "Show lint warnings on Verify" is off) for warnings and clearer errors. Lint fails for warnings too, so its result never stops the build; only `build` decides success. Upload is `build` then `program_board` (not attempted if the build failed). Repeated problems (lint and build flagging the same line) are dropped by `dedup`, keeping lint's. The engine's diagnostics map one to one (`info` shows as a warning); a failed step without an located error adds its message, plus the action's description (e.g. "No Alhambra II is connected. Connect the Alhambra II by USB, then retry."), as an error without a location, and its action code goes to `TaskOutcome.action`. The console shows the engine's live output: command lines dimmed with `$`, error lines red, warnings yellow, and the message of a failed step in red (not for design errors, whose message repeats the tool's line). A progress bar's redraws (one line each from the engine) are collapsed to the last one (`Console` in `engine/task.rs`, by the pattern `label [bar] n%`, TODO(revisit)). The engine's phases ("Synthesizing", "Placing and routing", "Writing flash" with its percentage) go to the status bar as `TaskEvent::Progress`. After success, the build's `resources_usage` and `timing` become the report: the UI logs "The design uses 27 of 7680 logic cells (0.4%)." and "Maximum clock speed: 194.4 MHz (sys_clk)." (`reportLines`, as Arduino's "Sketch uses …"), and the status bar summary ("Uses 0.4% of logic cells, max clock 194.4 MHz"); `ui/src/lib/buildReport.ts` uses plain per-family names (iCE40, ECP5, Gowin, Xilinx; unknown families use the toolchain's names).
- **Run Tests / Simulate** (toolbar flask and waveform icons, Shift+Cmd+T / Option+Cmd+T, Project menu, right-click on a testbench tab): `Task::Test` runs the engine's `test` with the chosen testbench or all `*_tb.v`/`*_tb.sv` as `testbench_files` (the engine runs every testbench, each stopped at its first failure, with a 10-minute default limit); each result becomes a `TestbenchResult`, its diagnostics (`$error`, `$fatal`, Apio's assertion lines, at file, line and time) are marked, and an `ending` of `timeout`, `sim_time_limit` or `no_finish` adds a plain note (`ending_note`). `Task::Simulate` runs the engine's `simulate` on one testbench with `layout_file` `<testbench stem>.gtkw` next to it: the engine runs it to the end, writes a default layout there unless the user saved one (zoomed around the first failure), and starts GTKWave detached, failing or not. A failing simulation also returns its `TestbenchResult`, so the status says "The testbench failed (GTKWave shows the signals): …" (`outcomeText`). Simulate uses the open testbench tab or the project's only testbench. `run_task` only accepts project files matching `project::is_testbench`. Testbenches follow the engine's rules (report failures with `$error`, never call `$dumpfile`; see the engine's `docs/tool-api.md`, Writing testbenches). New `*_tb.v` files start from a testbench template (`starterText` in `workingProject.ts`).
- **Auto Format** (Tools menu, Cmd+T, as in the Arduino IDE; Cmd+T was taken from Run Tests for this): formats the open Verilog/SystemVerilog file with the engine's `format` (Verible; `engine/format.rs`). `format_file` writes the text into a one-file scratch folder (`build_dir::prepare_single`, `~/.logix/format/`), formats it there, shows Verible's command line in the console, and returns the result. The editor applies it as one undoable edit (`Editor.replaceText`) and leaves the file unsaved. Messages match Arduino's: "Auto Format finished." / "No changes necessary for Auto Format." Verible's errors come back as the engine's diagnostics and are marked like build errors.
- **Connected devices** (Tools > Connected Devices…): the engine's `list_devices` lists the USB devices (`engine/devices.rs`), shown by `ui/src/lib/DevicesDialog.svelte` with Refresh. When Upload fails with the engine's `connect_board` action (`isBoardNotFound`), the status gives the engine's message and the console lists what is connected, with tips about cables and power (`deviceSummaryLines` in `ui/src/lib/devices.ts`). Which device Upload uses stays the engine's decision (the board list's "Connected" group only suggests; see Connected boards).
- **Connected boards** (as in Arduino IDE 2's board selector): while the window has focus and nothing runs, the UI polls `connected_boards` every 3 s (and on focus). It runs the engine's `list_devices` and matches the devices against the USB filters of the boards' default programming variants from `get_catalog` (`engine/devices.rs`, read once into `Catalog.usb_rules`): equal vid/pid, and the optional `product_regex` searched in the product name (the engine's rule). (Not one `list_devices` call per board with `matches_board`: that's 79 calls every 3 s.) A device matching boards by product name lists those (`exact`); otherwise its chip's boards without a product name are listed only if there are at most 3 (generic FTDI ids fit dozens). The board picker then starts with a "Connected" group, and "Connected" / "Not connected" next to it tells whether the selected board is plugged in. The board is never switched automatically. Scans pause during tasks since Upload uses the device. The fake backend's `__fake.connected` sets what's plugged in.
- **GTKWave to the front**: GTKWave is started in the background by the engine's `simulate`, so on macOS its window would stay behind Logix. `run_task` notes the GTKWave processes running before a simulation; afterwards (if a testbench result came back) `bring_gtkwave_to_front` (`commands.rs`) waits up to ~8 s for the new one and activates it through `platform::bring_app_to_front` (macOS: Logix yields activation, then the target is activated, which needs no permissions; native calls run on the main thread). The dev terminal shows `[logix] Brought GTKWave ...` or `Didn't find ...`.
- **Diagram** (Project > Show Diagram, Shift+Cmd+D): `Task::Graph` runs the engine's `graph` with the module as `top_module` (`main` by default) in the build folder (like Verify: unsaved edits, Stop, errors marked) and returns its `graph_file` (`_build/logix/graph.svg`) as `graphSvg`. The engine gives yosys absolute paths, so process labels would read `/Users/you/.logix/build/main.v:5.14-5.25`; `relative_paths` drops the folder (TODO(revisit): ask the engine to label them relative to the source folder). `ui/src/lib/DiagramDialog.svelte` shows it inside Logix as an `<img>` data URL (so nothing in the SVG can run), with Fit/zoom and a module picker (`projectModules`: modules in non-testbench Verilog files, `main` first). `run_task` only accepts plain identifiers as the module (`project::is_verilog_identifier`).
- **GTKWave layouts**: the simulation's source folder is the build folder, so the layout GTKWave opens (`main_tb.gtkw`, copied from the project if it has one) and saves is there. `build_dir::save_back_gtkw` copies `.gtkw` files without a generated-layout marker ("GENERATED AUTOMATICALLY BY LOGIX ENGINE", or Apio's "... BY APIO") back to the (saved) project folder, if the build folder belongs to that project and the file changed. It runs before each task (preparing clears the build folder) and when the window regains focus (`save_gtkwave_layouts`), and logs what it saved.
- **Live errors while typing**: Verible's language server (`verible-verilog-ls`, from the engine's `verible` package: `engine::program_path` reads the package's `bin_folder` from `get_engine_info`) runs with `--ruleset=none` (syntax errors only; Verible's style rules would flood beginners) and `--lsp_enable_hover=true`. The backend only relays messages (`src-tauri/src/language_server.rs` frames them; `lsp_start`, `lsp_send`, `lsp-message`/`lsp-closed` events). The UI speaks the protocol with `@codemirror/lsp-client` (`ui/src/lib/lsp.ts`: diagnostics, hover (own handler: skips empty answers and `tidyVeribleHover` drops Verible's "### data/net/var/instance" category title, keeping the name and e.g. "Type: reg [23:0]"), F12 jump to definition; not its formatter, since Auto Format uses Apio). The editor attaches each Verilog document through a compartment (`lspSlot`), with the file's real path as its address (a placeholder for unsaved projects). Only the shown tab is open in the server. It starts after the FPGA tools are ready and restarts if it stops; Settings can turn it off ("Check code while typing", default on: `lsp_stop`) and hover is off unless "Show info when hovering" is on (`setHoverEnabled`), both applied on OK without a restart; the fake backend never answers, so e2e tests and screenshots run without it. Live diagnostics and Verify's share the editor's lint markers; each replaces the other's.
- **Diagnostics**: every task's problems come from the engine as diagnostics (file relative to the source folder, line, column, severity, text; `info` shows as a warning), mapped one to one by `diagnostics` in `engine/task.rs`. Build folder file names equal project file names, so no path mapping is needed. The editor shows them with `@codemirror/lint` (gutter, underline, hover). Tabs with problems get a red or yellow underline, and a failed task jumps to the first error.

## Backend interface

All Tauri commands are in `commands.rs`, registered in `lib.rs` and wrapped in `ui/src/lib/backend.ts` (same names in camelCase). Failures reach the UI as `UserError { message, details }` (plain-language message, technical details).

- **App and setup**: `app_info` (name, version, platform, `platformSupported`); `setup_apio` (sets up Apio, then the engine; Channel of `SetupEvent`: stage `checking` / `downloadingApio` / `installingPackages` / `downloadingEngine` / `installingEnginePackages` / `ready`, download bytes, engine install `progress` (`message`, `percent`), output lines). The running engine is kept in `AppState.engine`.
- **Catalog**: `get_boards` (`id`, `description`, `arch`; the engine's boards), `get_examples` (`{ examples: [{ board, name, description }], hidden }`), `open_example(board, name)`, `open_bare_minimum(board)`.
- **Projects**: a project travels as `ProjectDoc { dir | null, templateDir | null, name, files: [{ name, text }], board | null, starter }`. Commands: `new_project(board?)`, `open_last_project`, `open_project_dialog`, `open_project_at(dir)`, `save_project` (with removed files), `save_project_as_dialog`, `show_project_folder`, `check_file_name(name, existing)` (error text or null), `set_last_board`.
- **Tasks**: `run_task(task, testbench?, key, sourceDir?, projectDir?, files, board, Channel of TaskEvent)` with task `build` / `upload` / `test` / `simulate` / `graph`; a `TaskEvent` is `{ kind: line, line }` or `{ kind: progress, message, percent? }`. It returns `TaskOutcome { ok, diagnostics, testbenches: [{ name, passed }], report, cancelled, graphSvg, seconds, action? }` (`action`: the engine's suggested action code on failure, e.g. `connect_board`). A diagnostic is `{ severity: error | warning, file?, line?, column?, message }`; the report `{ arch, resources: [{ name, used, available }], clocks: [{ name, fmaxMhz }] }`. Also `cancel_task`, `format_file(name, text)` (`{ ok, text?, diagnostics }`), `save_gtkwave_layouts(key, projectDir)`.
- **Devices**: `scan_devices` (`{ usb: [{ vid, pid, manufacturer, product, serialNumber }] }`), `connected_boards` (`[{ board, exact }]`).
- **Language server**: `lsp_start`, `lsp_send`, `lsp_stop`; events `lsp-message`, `lsp-closed`.
- **Settings**: `get_preferences`, `set_preferences` (returns the stored values), `choose_folder_dialog`.
- **Window**: `ask_confirm`, `ask_save_changes` (`save` / `discard` / `cancel`), `set_document_state(name, dirty)`, `close_window`, `show_editor_menu(canGoToDefinition)`, `show_output_menu`, `log_output(lines)`.
- **Events** to the UI: `menu`, `open-recent`, `apio-output`, `close-requested`, `lsp-message`, `lsp-closed`.

## CI and release workflows

Use the current major versions of GitHub's actions (`actions/checkout`, `setup-node` with `lts/*`, `upload-artifact`, `download-artifact`, `setup-python`, `upload-pages-artifact`, `deploy-pages`), `dtolnay/rust-toolchain@stable` with `clippy, rustfmt`.

- **`test.yaml`**: on every push and pull request, manually, and daily at 00:00 UTC; a newer run for the same ref cancels the older one; matrix macos-15, macos-26, macos-latest with `fail-fast: false`, 30 min. Steps: checkout, Node (npm cache), Rust, `npm ci`, `npx playwright install webkit`, `scripts/test.sh`.
- **`build-pre-release.yaml`**, three jobs:
  - `prepare` (Ubuntu): release tag `yyyy-mm-dd` and package tag `yyyymmdd`; an early check that no stable release has that tag; repo `owner/repo` (lowercase, from the `origin` URL), branch and full commit; the version from `tauri.conf.json`. Writes `BUILD-INFO.json` (`package-name` logix, `description` (the motto), `logix-version`, `repo`, `repo-branch`, `repo-commit`, `release-tag`, `package-tag`, `build-time`, `builder-workflow`, `workflow-run-id`, `workflow-run-number`), formatted, as the `build-info` artifact.
  - `build-darwin-arm64` (reusable workflow, `macos-latest`, 60 min): checks it runs on darwin/arm64, adds `target-platform` to the build info, checks out exactly `repo-commit` into `_repo/` (so every platform builds the same commit), sets up Node and Rust, `npm ci`, installs WebKit, runs `scripts/test.sh`, builds the .dmg, requires exactly one and names it `logix-darwin-arm64-<package tag>.dmg`. Then it checks the .dmg: `hdiutil verify`, mounts it, finds the `Applications` link and `.DS_Store`, and `codesign --verify --deep --strict` plus "Signature=adhoc" on `Logix IDE.app`. Artifact `logix-darwin-arm64`.
  - `pre-release` (Ubuntu): downloads all artifacts into `_artifacts/`, scans the .dmg files with ClamAV, makes `build-info.txt` (aligned `key : value`), an installers table (system, architecture, installer type, link), a run summary (build info, commit link, release link), and the release notes: the motto in bold, then links to the product page and the docs; macOS install steps (download to Downloads, the `xattr -c` command and why, drag to Applications, the first start downloads the FPGA tools and may take a few minutes); uninstalling (drag to the Trash; `~/.logix` holds the tools and settings, not projects); the installers table; the build info; and "About these releases" (daily pre-releases, about 5 kept, made stable by changing the status from Pre-release to None). Then it deletes all but the 5 newest pre-releases, deletes a pre-release with today's tag, and creates the pre-release (name = tag) with the .dmg and `BUILD-INFO.json` listed by exact name, so a missing file fails the run.
- **Actions**: the shared ones in `openlogix/.github` (see that repo's `CLAUDE.md` for each action's inputs and behavior). Jobs check out this repo only when a step needs its files (`prepare` for `get-repo-info`, the build job's `_repo/`).
- **`publish-docs.yaml`**: Ubuntu, Python 3.14, `pip install -r docs/requirements.txt`, `mkdocs build --strict` into `_site/`, then `upload-pages-artifact` and `deploy-pages` (permissions `pages: write`, `id-token: write`; environment `github-pages`). The repo's Pages source must be set to GitHub Actions.
- **Open Recent / Show Project Folder**: `settings.json` keeps up to 10 recent project folders (`recentProjects`, newest first), updated whenever a project is opened or saved. `menu::refresh` rebuilds the menu bar so File > Open Recent stays current; its items are `recent:<index>`, emitted to the UI as `open-recent` with the folder, then `open_project_at` loads it (a folder that can't be loaded is dropped from the list). Project > Show Project Folder (Option+Cmd+K, as in Arduino) opens the folder via `Platform::reveal_folder` (`open` on macOS).
- **Stop** (toolbar button, always shown and greyed out while nothing runs; Project > Stop, Cmd+.): `cancel_task` triggers the `CancellationToken` the running `run_task` holds (`AppState.task_cancel`). The engine call then sends MCP's cancel and the engine stops its tools (see the engine adapter). A stopped Verify skips its remaining steps; the status says "Build stopped."
- **Editor right-click menu** (as in Arduino IDE 2, shorter): Go to Definition (F12; greyed out without live checking or outside Verilog files), Cut/Copy/Paste/Select All, Comment/Uncomment (Cmd+/), Auto Format. It's a native menu (`menu::show_editor_menu`, command `show_editor_menu`), not HTML, because the system Paste works without WebKit's paste confirmation. Right-click first moves the cursor to the click unless it's inside the selection (`Editor.svelte`). Custom items come back as `menu` events (`go-to-definition`, `toggle-comment`, `auto-format`), which the Edit menu also has. The fake backend records the last menu in `__fake.editorMenu`.
- **Select All / Copy in the output**: the output pane is focusable (`tabindex`). Edit > Select All (Cmd+A) is a custom item (`select-all`, not the system one, which selects the whole window): the UI selects all of the focused text field, the output pane (`selectOutput`), or else the editor. Right-click in the output shows a native menu (`menu::show_output_menu`): system Copy, Select All (`output-select-all`), Clear Output (`clear-output`). File links in the output are `<a>` elements (not buttons) so they're selectable and copied with the text.
- **Links in the output**: `file:line` references to project files (bare file names, not full paths) become links that jump to that line (`addLinks` in `ui/src/lib/ansi.ts`).
- **Settings** (Logix IDE > Settings…, Cmd+, on macOS; File > Settings… elsewhere), laid out like the Arduino IDE's Preferences (`ui/src/lib/PreferencesDialog.svelte`, Cancel / OK, applied on OK): projects folder location (Arduino's sketchbook location; used by New/Open/Save As through `project::default_projects_root`), editor font size, interface scale (automatic or %), theme (System/Light/Dark), "Show lint warnings on Verify", "Check code while typing" (default on) and, under it, "Show info when hovering" (default off; see Live errors). Stored in `settings.json` (`settings::Preferences`; values equal to the default are stored as unset, and `set_preferences` checks ranges). The backend applies the scale (`set_zoom`) and window theme at startup and on save (`apply_window_preferences`); the UI sets `data-theme` on `<html>` (CSS in `app.css`) and `--editor-font-size`, and passes `dark` to the editor.
- **Help menu**: links to the Logix user docs (see "User documentation"), Apio's docs for going further, and Logix Website (the product page) / Logix on GitHub / Report a Problem (`HELP_LINKS` in `menu.rs`, opened with `Platform::open_url`, `https://` only). About Logix IDE (macOS app menu; Help elsewhere) shows the version, the motto, the Apio release, the Arduino notice, and links to the product page.
- **Busy / ready** (status bar): one indicator for everything. `isBusy` in `App.svelte` (setup not ready, a task `running`, Auto Format, or a file `activity`) shows a spinner, and `statusText` shows what's going on; when idle, the last result (`status`) or "Ready.". Slow file operations (opening an example or Bare Minimum, New, Open Recent, Save, the starter upgrade) go through `during(label, work, done)`, which sets `activity` and then the done text. Verify and the other actions are disabled while busy (`canRun`).
- **End of a command's output**: when Verify, Upload, Run Tests, Simulate, Show Diagram or Auto Format ends (even failed or stopped), the output pane gets the status bar's result line (green after success, red after an error) and then "Ready." (`logDone` in `App.svelte`), so the output says when it's done, like startup's "Ready.".
- **Output (console) visibility**: View > Toggle Output (Cmd+J) or the Hide/Show button on the status bar hides the console and divider, leaving the one-line status bar. The choice is remembered (`localStorage`, like the console height). The console comes back by itself when Verify, Upload, Run Tests or Simulate starts, and when Auto Format or setup fails (`showOutput()` in `App.svelte`), as in Arduino IDE 2.
- **Reopening the last project**: `src-tauri/src/settings.rs` keeps IDE settings in `~/.logix/settings.json` (unknown fields preserved). Opening, saving or Save As records the project folder; at startup the UI calls `open_last_project` and falls back to a new project (with a console note) if there's none or it can't be loaded.
- **Always a board**: new projects get the given board, else the last chosen (`lastBoard`), else `apio::DEFAULT_BOARD` (`alhambra-ii`, FPGAwars' canonical board), so a first start opens the Alhambra II blinky. Only a project opened from disk without a board shows "Select board…".
- **Welcome panel**: while the tools aren't ready (first-run install, failed setup) and there's nothing of the user's (`welcome` in `App.svelte`), the editor area shows "Welcome to Logix IDE / \"The Arduino experience, for FPGAs\"" and "Getting the FPGA tools ready…" (or a pointer to the setup error) instead of a placeholder that can't be built; tabs and editor are hidden (not unmounted) and Verify etc. are disabled. Once ready, the untouched placeholder is upgraded to the board's starter.
- **New projects** (File > New, and at startup when there's no last project): at startup the UI waits for the tools (`ensureProject` in `App.svelte`, after the catalog loads) so blinky shows directly instead of the generic placeholder; a long first-run install, failed setup or unsupported platform gets the placeholder right away. `new_project(board)` uses the given board, or else the last chosen one (`settings.json` `lastBoard`, saved by `set_last_board` on every board change). If the tools are ready and the board has a starter example (`blinky`, else `ledon`: `apio::starter_example`), the project starts from it (`starter: true`, `templateDir` set, named "untitled"), so it has the board's pin file and builds right away; otherwise it gets the generic starter `main.v`. A generic starter made before the tools were ready is upgraded once the catalog loads while it's untouched (`isUntouchedStarter`: never edited or saved). Changing the board never replaces files (as in Arduino): `setBoard` holds it in `pendingBoard` and opens the Examples dialog for that board only (`onlyBoard`; "Keep Current Files" or Esc applies the board, opening an example brings its own board, so "Save changes?" is only asked about real edits). A missing pin file is explained in plain words (`friendly` in `ui/src/lib/tasks.ts`).
- **Board picker** (`ui/src/lib/BoardPicker.svelte`, like Arduino IDE 2's board selector; replaced a native `<select>`, which can't report picking the current board): a button with the board's name opens a searchable list (combobox + listbox, arrows/Page/Enter/Esc), "Connected" first, then all boards grouped by FPGA architecture (`Board.arch` from `apio api get-boards` `fpga.definition.arch`; groups and order in `ui/src/lib/boards.ts`: iCE40, ECP5, Gowin, Xilinx, then others). Picking any board, the current one included, calls `setBoard`. Architecture groups are collapsible (not "Connected"), in the picker and in the Examples dialog's boards column (`groupByArch`); the expanded ones are shared by both and remembered in `localStorage` (`ui/src/lib/expandedGroups.svelte.ts`, all collapsed by default), opening a list expands the current board's group, and a search shows matches in all groups.
- **Board**: chosen in the toolbar's board picker and stored in `logix.json`. Changing it offers the board's examples (see New projects) and, if the files are kept, marks the project as unsaved.
- `src-tauri/src/menu.rs`: native menu bar. New/Open/Save/Save As are emitted to the UI as `menu` events; Close and Quit go through the window-close flow. File dialogs and the "Save changes?" prompt run in Rust (`tauri-plugin-dialog`), so the UI needs no dialog or file system permissions.
- **Closing with unsaved changes**: the UI reports the dirty flag with `set_document_state`. When it's set, `CloseRequested` is blocked and a `close-requested` event goes to the UI, which asks Save / Don't Save / Cancel and then calls `close_window`.
- `Apio::command()` removes inherited `APIO_*` environment variables (except when `LOGIX_APIO_BIN` is set), so a user's own Apio settings never affect the IDE.
- `src-tauri/tauri.conf.json`: app name/identifier, window, dev server port (1420, must match `ui/vite.config.ts`), bundle settings.
- `src-tauri/capabilities/`: Tauri permissions granted to the UI. Keep them minimal; prefer adding Rust commands over granting the UI file system or shell access.
- `src-tauri/icons/`: app icons, generated from `icon-source.png` with `npx tauri icon src-tauri/icons/icon-source.png` (delete the generated `android/` and `ios/` folders). The source is the Open Logix brand icon for Logix IDE (org site `docs/brand/ide.svg`: a `#10B981` to `#0F766E` diagonal gradient tile with rx 16 of 64, and a white window (rect 14,17 36x30 rx 6, stroke 4.5) with a filled play triangle), drawn by `swift src-tauri/icons/make-icon-source.swift src-tauri/icons/icon-source.png`; keep it equal to the brand icon (also used as the docs logo). The 64-unit drawing is scaled to about 824 px and centered on a transparent 1024 px canvas, Apple's icon size; a full-bleed square looks oversized in the Dock next to other apps.

## Development notes

- **Developer Apio override**: set `LOGIX_APIO_BIN=/path/to/apio` to skip the bundle download and use a local Apio (e.g. when testing `apio api` changes). The IDE's private `APIO_HOME` is still used.
- **Testing first-run setup** without touching the real `~/.logix`: run with a temporary `HOME` (keep `CARGO_HOME`/`RUSTUP_HOME` pointing at the real ones). Symlink `<tmp-home>/.logix/apio/home` to an existing Apio home, and `<tmp-home>/.logix/engine` to an existing engine folder, to avoid re-downloading about 650 MB of packages each.
- **Log**: backend messages go through `log!(...)` (`src-tauri/src/logging.rs`), which prints `[logix] ...` to the dev terminal and appends it with a UTC time to `~/.logix/logs/logix.log` (one file per run, the last 5 kept as `logix.1.log`...), since an app opened from Finder has no visible stderr. It logs the startup header (versions), every Apio run (`Run:` / `Exit:`, in `process::run_streaming`), every error returned to the UI (`From<anyhow::Error> for UserError`), crashes (panic hook), the existing status lines (setup, language server, GTKWave), and every output pane line as `| <line>` (`log()` in `App.svelte` batches them to `log_output`; colors removed; above 10 MB per file only messages are kept). Help > Show Log Folder opens it; Help > Report a Problem pre-fills the issue text asking for `logix.log`. Use `log!` instead of `eprintln!`. There's no way to see the window from automation, so ask the user to confirm UI changes visually.

## Open items

Things deliberately postponed. Revisit them when the related feature is worked on. Code that depends on one is marked `TODO(revisit)`.

- **Hidden examples**: 18 of Apio's 164 examples (Apio `2026-10-22`) are hidden because Logix doesn't support subfolders, several board setups (envs), or `apio.ini` settings beyond board/top-module/default-testbench. Examples hidden this way include `bcd-counter`, `multi-env`, `speed-test` and the only `blinky` for `alinx-ax7035` and `sipeed-tang-primer-20k`. Revisit to support more of them. Rules: `example_is_supported` in `src-tauri/src/apio/catalog.rs`. The console reports the hidden count when examples load.
- **Resource names in the build report**: `ui/src/lib/buildReport.ts` maps Apio's per-family resource names (e.g. `ICESTORM_LC`, `TRELLIS_COMB`) to plain ones. That's FPGA knowledge that ideally comes from Apio; consider asking for plain labels and a "main resource" flag in `apio api get-build-report`.
- **Serial ports**: Connected Devices lists USB devices only. The serial ports came from Apio and were dropped with it (the user's decision); add them back if the engine lists them (`list_devices` `kind` `serial`).
- **Example details from Apio**: the compatibility check reads Apio's package folder directly. Consider asking Apio to include per-example details (envs, settings, subfolders) in `apio api get-examples`.
- **USB drivers and permissions** (Windows, Linux): boards often need a driver (Windows) or udev rules (Linux) before Upload can see them. The requirements call for guided setup inside the IDE using `apio drivers`; build it on top of Tools > Connected Devices when those platforms are added.
- **Stop on Windows**: `platform::stop_process_tree` only stops Apio itself on non-Unix systems; on Windows, use a job object so the tools Apio started stop too (marked `TODO(revisit)`).
- **Notarization**: macOS builds are ad-hoc signed, so users must run an `xattr` command on the downloaded `.dmg`. Signing with an Apple Developer ID and notarizing (secrets in GitHub only) removes that step.
- **Logix Engine**: Logix IDE is moving from calling Apio directly to the org's Logix Engine (an MCP backend for building, testing and simulating FPGA designs and programming boards; repo `openlogix/logix-engine`), in four steps: (1) download, start and set up the engine (done), (2) board selector from `get_catalog`, Verify, Upload, live output and Stop (done), (3) Run Tests, Simulate, Auto Format and Show Diagram, plus Connected Devices and the board list's Connected group (`list_devices` and the catalog's USB filters) (done), (4) the IDE's own examples, removing Apio, docs and the product page. Until step 4 the product page says it's built on Apio. Boards: the engine has 79 of Apio's 109 boards (those whose programmers it supports: `openfpgaloader`, `iceprog`); the others aren't offered until the engine supports them. Engine requests worth making: mark progress bar redraws in `logix/output` (e.g. a `redraw` field), so the IDE can drop its pattern; diagram labels relative to the source folder. (Done in the engine: each installed package's `bin_folder` in `get_engine_info`, for the language server.) Decided for Simulate (not done yet; an engine change): a re-run should reuse the open GTKWave window for that testbench (bring it to the front and reload, keeping the user's unsaved view), never close it; the bundled GTKWave 4 has no remote control, so check first whether it can reload an open window reliably, and if not, keep opening a new window and say in the output that the older one shows the previous run. The "one Apio adapter" rule keeps the move to `apio/` and `engine/`.
- **Engine pin is a pre-release** (`TODO(revisit)` before an IDE release that uses the engine): during development the IDE pins a daily engine pre-release, which an engine commit on the same day replaces and which is deleted after about 5 newer ones. A replaced same-tag package isn't downloaded again (the URL is the same): delete `~/.logix/engine-bin` to get it. Before an IDE release, make the pinned engine release stable on GitHub (untick pre-release) and have the IDE check the package's size and SHA-256.
