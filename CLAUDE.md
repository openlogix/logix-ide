# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The AI spec is the source

The **AI spec** is this file plus any files it points to (e.g. `.claude/` files added later). It is the real source of the repo. A capable AI agent should be able to regenerate everything else from it, with equivalent behavior: the app, tests, GitHub workflows and actions, scripts, packaging config and docs.

- **Detailed enough, not too detailed.** Record what and why: requirements, decisions with their reasons, contracts between parts (commands and events, file formats, names, paths, pinned versions), verified facts about external tools (Logix Engine, Tauri, GitHub), conventions, and the non-obvious lessons (workarounds, "why not X"). Leave out what follows from these or from standard docs, such as line-by-line code. Test: if an agent regenerating the repo would likely get it wrong without a sentence, keep the sentence; otherwise leave it out.
- **Same commit.** Every change to behavior, workflows, scripts or decisions updates the AI spec in the same commit. Remove what no longer holds.
- **No personal info.** Nothing that identifies or locates a person: no names, emails, machine-specific paths, account details or private notes. Use placeholders (e.g. `/Users/you`).
- **Pull requests are rules or prompts.** Ideally a pull request changes the AI spec (a requirement, rule or decision with its reason), or gives the prompt to run, rather than hand-written code; the code is then generated from it. A pull request that does include code must also include the AI spec change that explains it, since code the AI spec doesn't account for would be lost when the repo is regenerated. Its description gives the prompt(s) used. When working on a code-only contribution, first turn it into the rule it implies and add that to the AI spec.

## The reference frontend

Logix IDE is the reference frontend for Logix Engine (the rule is in the website repo's `CLAUDE.md`, shared Open Logix rules): much of its logic, such as board and board variant choice, connection status and device choice, Upload, the build report, problems and the console, is what any frontend needs, including frontends outside Open Logix. So:

- **Engine first.** Logic every frontend would need, that doesn't depend on the IDE's own model (its project folders, examples, look), belongs in the engine. When the IDE repeats engine knowledge, such as FPGA family names, pin file extensions or the toolchain's resource names (all moved to the engine on 2026-11-05: `get_catalog` families, `build` `resources_summary`), fill the gap in the engine and use it here.
- **An example to read.** The engine adapter (`src-tauri/src/engine/`) and the UI helpers that turn engine results into what users see (`ui/src/lib/boards.ts`, `devices.ts`, `buildReport.ts`, `tasks.ts`, `variants.ts`) stay small, commented and tested, so another frontend can follow or copy them (MIT or Apache 2.0). The engine's `docs/tool-api.md` (Recipes for frontend developers) links to them: keep those links working when renaming or moving these files.
- **No private knowledge.** The IDE uses only what the engine's tool API documents, never its internals, so what works here works for any frontend.
- **Easy to explore.** The repo (code, docs, this spec) is written for people and AI agents who develop hosts and frontends, inside and outside Open Logix: clear names and layout, each module's purpose and its engine calls explained at the top of the file and in this spec, and nothing that needs Open Logix's private context to understand.

## Project goal

**Name: Logix IDE.** The product is "Logix IDE", as on its product page (www.openlogix.org/ide/) and in the Open Logix family (Logix Engine, Logix CLI, ...). Use the full name wherever the product is named as such: the app and bundle name (`productName`, so `Logix IDE.app`), window title, About box, the macOS app menu (About/Quit Logix IDE), installer text, page titles (README, docs home and Installing; the docs site is "Logix IDE Docs", so it isn't taken for the main page), and release notes. Never "Logix" alone for the product (the user's rule, 2026-11-10): "Logix" is short for Open Logix, the whole project, so write "Logix IDE" in running text too, in the docs, the UI's messages, release notes, code comments and this spec ("Open Logix" for the project; the rule is in the website repo's `CLAUDE.md`). File and folder names keep their spelling (`~/.logix`, `logix-ide.toml`, `~/Documents/OpenLogix/IDE`). Internal names stay lowercase `logix` and don't change with the product name: `~/.logix/`, `logix.log`, the `logix-darwin-arm64-*.dmg` file name, the `logix` npm/Cargo package, the bundle identifier, (renaming them would break existing installs and projects). The default projects folder is `~/Documents/OpenLogix/IDE` (2026-11-10, the website repo's Folder names rule; `project::builtin_projects_root`).

**Motto: The Arduino experience, for FPGAs.** Use it, without quotes (decided 2026-11-08; it was quoted before), wherever Logix IDE describes itself: the docs (site description and home page), the About box, the release notes, package descriptions, and any new place like that (e.g. a README or app store text).

**Mentioning Arduino**: Logix IDE mentions Arduino only to describe how it feels (the motto, "as in the Arduino IDE"). Don't use "Arduino" as a name for anything of Logix IDE's, or Arduino's logo or artwork. Keep the notice "Logix IDE is not affiliated with or endorsed by Arduino. Arduino is a trademark of Arduino SA." where Logix IDE presents itself: README (Trademarks), the docs footer (`copyright` in `mkdocs.yml`) and the About box (`menu.rs`).

A minimalist, Arduino-IDE-like desktop IDE for FPGAs. Users write **Verilog** (instead of C/C++), and the IDE uses **[Logix Engine](https://github.com/openlogix/logix-engine)** (the org's MCP backend for FPGA operations, repo `openlogix/logix-engine`) as its toolchain (instead of gcc / arduino-cli). Logix IDE used [Apio](https://github.com/FPGAwars/apio) until the move to the engine (steps 1 to 4, done); the engine runs Apio's toolchain packages with Apio's commands, so builds match Apio's.

### Requirements

- **Look and feel similar to the Arduino IDE**: a simple editor with a small set of obvious actions (e.g. verify/build, upload), a board selector, an examples menu, and an output console. Keep it minimal; ease of use for beginners comes before power-user features.
- **Easy to install and use** on three platforms, all of them first-class:
  - Linux x86-64
  - Windows x86-64
  - macOS ARM (Apple Silicon)
- **The installer is the only thing users need.** No manual installation of prerequisites (no Python, Node, Rust, runtimes, Homebrew or package managers). Everything else either ships inside the installer or is fetched automatically by the IDE at runtime with progress shown (Logix Engine and its packages; see Design notes). Implications:
  - The released app must not depend on anything from the developer machine (dev tools, Homebrew libraries, `PATH` entries). By default it uses only the engine it downloaded, the GitHub package of the pinned release. That need not hold when diagnostic and debug features of the IDE or the engine are turned on at runtime, such as a local engine (Dev engine, below). Those features are not meant for normal use by end users: they are for Open Logix developers, for users an Open Logix developer guides through them, and for manual and automated testing of Open Logix components (the user's decision, so GitHub-built IDEs can be diagnosed too; a stable release is a pre-release declared stable, the same binary, so a build-time switch couldn't tell them apart).
  - Windows: the installer must handle the WebView2 runtime itself (Tauri's bundled bootstrapper or offline installer), not ask the user to install it.
  - Linux: prefer formats that work out of the box (AppImage); `.deb` dependencies must resolve automatically through the package manager.
  - Board USB drivers / permissions (Windows drivers, Linux udev rules) are set up from inside the IDE with guided steps, not as a manual pre-install step.
- **Boards**: users choose a target board from the boards Logix Engine supports (`get_catalog`).
- **Examples**: users can browse and open Logix IDE's examples, as the Arduino IDE does with its examples. **Decided** (with reasons): the IDE keeps its own project model and examples (the engine has no project model or examples; see the website repo's `CLAUDE.md`). Examples are per board (a folder per board per example), imported from Apio's examples for the engine's boards and relicensed to Apache-2.0 (the user confirmed the right to do so), now MIT or Apache-2.0 like the whole repo. They're bundled in the app (in this repo, built into the binary, like Arduino's built-in examples: offline and always matching the IDE). See Examples.
- **Core workflow**: edit Verilog → Verify (lint and build) → Upload (program the board).
- **Testbenches**: write testbenches, run them (Run Tests) and view their signals in GTKWave (Simulate); see Run Tests / Simulate.

### Platform rollout

Development starts on **macOS ARM**, and that is the only platform implemented, built and tested at first. Windows x86-64 comes next, with Logix Engine (Milestone 3), then Linux x86-64 (Milestone 4; decided 2026-11-10, the phases are in the engine's `docs/requirements.md`, Acceptance and phasing). Both must be addable without restructuring:

- Keep platform-specific code (engine package names, data directories, executable permissions, macOS quarantine handling, packaging) behind small per-platform functions or modules, selected in one place. Don't scatter OS checks through the code.
- Use cross-platform APIs for paths and processes (no hardcoded `/` separators, shell-specific commands or macOS-only paths in shared code).
- Where a Windows or Linux branch isn't implemented yet, make it fail clearly ("not supported yet") rather than silently doing the macOS thing.
- CI and release start with macos-arm64 only. The other build-matrix entries are added when those platforms are implemented.

### Design notes

- The IDE is a front end. Synthesis, place-and-route, programming, simulation, formatting, diagrams, device scanning and the board catalog all come from Logix Engine's tools. Don't reimplement toolchain logic or hardcode board lists the engine provides.
- **Users should not need to learn the toolchain**, just as Arduino users don't need to learn gcc. Don't expose engine or tool concepts in the UI unless there's no way around it.
- **Project on disk** (decided): a project is a folder with any name (spaces OK). The main file is `main.v` (or `main.sv` for SystemVerilog) with top module `main` (one fixed rule, nothing to configure, like Arduino's `setup()`/`loop()`). It's always the first tab and can't be renamed or deleted; new projects get `main.v`. Folders are flat: top-level source files (`.v .sv .vh .svh` and the pin constraint formats `.pcf .lpf .cst .xdc`, the formats Logix Engine supports) appear as editor tabs, with `main.v` first; testbenches are `*_tb.v`/`*_tb.sv`. Anything else in the folder (subfolders, data files, docs) is kept as is and goes along to builds. The Save As dialog starts next to the project's own folder (the folder holding it; `save_project_as_dialog`'s `project_dir`, apart from `source_dir`, the folder whose other files are copied, which for a project from an example is the example's), else in the projects folder (a project never saved, even one from an example), never inside a Logix IDE project (`project::save_as_start`), and suggests a name nothing there has yet: "untitled" or "<name> copy", else with " 2", " 3"… (`project::unique_name`), so accepting the suggestion never replaces anything (the user's request: the fixed names collided with existing projects). Save As onto an existing folder (the save dialog asks "Replace?" first) moves that folder to the Trash (`platform::move_to_trash`, crate `trash`, recoverable) and saves there, but only if it's a Logix IDE project or an empty folder (hidden files aside), and never a folder holding the project being saved (`project::check_replace`); anything else is refused with a plain message, so a mistyped name can't throw away other files. Save As onto the project's own folder saves it in place, as Save does, with nothing trashed (`project::save_as`; the user's decision: trashing it first would lose the other files Save As copies, and in place gives the same result). Save As also refuses a location inside a Logix IDE project (the current one or any folder with a project file above it: `project::enclosing_project`), since a nested project would be copied into its own builds (and, inside the source, into itself). File names can't contain spaces or path separators; the rules live in `project::check_new_file_name`. Creating, renaming and deleting files are held in memory and applied on save, like text edits, so "Don't Save" leaves the folder untouched. The project file is `logix-ide.toml` (see Files Logix IDE writes). New projects default to `~/Documents/OpenLogix/IDE/`. Code: `src-tauri/src/project.rs`.
- **Simple project model**: the user's project (the "sketch") is the IDE's own simple model. At build/upload/sim/test time, the IDE copies the user's sources (unsaved edits included) into a build folder, runs Logix Engine on it with the board and top module, and shows the results mapped back to the user's files (e.g. error line numbers).
- **Asking for engine changes is welcome.** When an engine change would make Logix IDE simpler or more robust, make it in the engine repo (its `CLAUDE.md` and `docs/tool-api.md` rule; the tool API only adds, never breaks) rather than working around it in the IDE, and note a temporary workaround (`TODO(revisit)`) if the IDE needs one meanwhile.
- **Logix Engine delivery**: the installer contains only the IDE. At startup the IDE downloads the pinned engine release (first launch, or when the pinned URL changes) and starts it. Pinned in `package.json` `appConstants.engineReleaseRepo` / `engineReleaseTag` (`openlogix/logix-engine`), checked by `build.rs` and passed in as `engine::ENGINE_RELEASE_REPO` / `ENGINE_RELEASE_TAG`; a test checks they match. The package is `https://github.com/<repo>/releases/download/<tag>/logix-engine-<platform>-<yyyymmdd>.tgz` (engine platform ids `darwin-arm64`, `linux-x86-64`, `windows-x86-64`), with one top-level `logix-engine/` folder holding the `logix-engine` executable and `LICENSE`. The IDE launches it as `logix-engine --engine-folder ~/.logix/engine` and talks MCP over stdin/stdout (crate `rmcp`, the client side of what the engine uses, over the child's pipes as an async reader/writer pair; see the engine adapter for why); the engine's stderr goes to the IDE's stderr and it writes its own log in `~/.logix/ide/engine/logs/`. Setup calls `get_engine_info` (logs the engine version and log file) and, if a package isn't `installed`, `install_packages` with a progress token: the engine reports one phase per package ("Installing oss-cad-suite") on a scale of 100 per phase, so the phase's percentage is progress modulo 100. Both downloads (engine and packages, about 650 MB) show progress, are retryable (a Retry button re-runs setup; downloads don't resume) and fail with a plain-language message. Once installed, startup is offline-safe (`get_engine_info` is local). The engine's rules that matter to the IDE: its folder's last name must contain "engine", and build folders need "build" in one of their last two names. The engine's `docs/tool-api.md` is the source of truth for its tools.
- **Logix Catalog (done, 2026-11-08):** the engine's boards come from the `logix-catalog` repo (its `docs/model.md` is the board format, `docs/design.md` the reasons): a board file per board, typed `resources` in place of `pin_groups`, `name` in place of `description`. A project's custom boards are its `boards/` folder (see The project's own boards). System Info shows the catalog version: it's a line of the engine's `report` ("Board catalog: Logix Catalog <date> (<commit>)"), so the IDE has nothing to add. The engine pin must move to an engine release with this change before the IDE ships it.
- **Dev engine** (a diagnostic feature, following the Open Logix convention in the website repo's `CLAUDE.md`: developing the IDE and the engine together, manual and automated testing, or diagnosing any IDE against a known engine, whether run from a local checkout or installed from a GitHub-built package): in every build, setup uses the engine binary named by `LOGIX_DEV_ENGINE_BINARY` instead of the pinned release, with its own engine folder `~/.logix/ide/dev/engine` (never the released engine's packages; the first run downloads its own). Setup sends `SetupEvent::DevEngine { path }`, and the UI shows a banner for the whole session ("Using a local Logix Engine, for diagnosis: <path>. Start Logix IDE normally to use the regular engine.", `role="status"`, amber), so it's never forgotten while diagnosing; the console says it too. A value that isn't a file is a setup error. From a local checkout, `scripts/run.sh --engine-repo-dir <engine clone>` builds the engine and sets it, or set it yourself (`LOGIX_DEV_ENGINE_BINARY=<path> scripts/run.sh`; the script passes it on). The `#[ignore]`d real-engine tests take the engine from the same variable. An installed macOS app sees the variable only when started with it, e.g. `open -a "Logix IDE" --env LOGIX_DEV_ENGINE_BINARY=<path>` after quitting Logix IDE (Finder and the Dock never pass shell variables). The fake backend's `/?devEngine` shows the banner. `scripts/run.sh --engine-repo-dir <folder>` runs `cargo build` (debug) in that local engine clone and sets the variable to its `target/debug/logix-engine` (names chosen by the user: `-dir` because it's a local folder, not a GitHub repo; BINARY, not EXE, which sounds Windows-only). Restart `run.sh` after changing the engine. Code: `dev_engine_binary` and `Layout::dev_engine_folder` in `engine/mod.rs`.
- Cross-platform behavior matters a lot: watch path handling (spaces, non-ASCII, Windows drive letters), per-user data directories, executable permissions on downloaded files, macOS quarantine of downloaded binaries, and USB permissions on each OS.

### Where builds happen

- **Release builds (installers, signing, notarization) are made only by the GitHub Actions build workflow**, never on a developer machine. Signing secrets live only in GitHub secrets.
- **Pre-releases**: `.github/workflows/build-pre-release.yaml` (on every push to `main`, daily at 00:00 UTC, and manual; `concurrency` cancels a running build when a newer one starts) uses the shared Open Logix actions from the `openlogix/.github` repo, as `openlogix/.github/actions/<name>@v1` (e.g. `get-release-and-package-tags`, `ensure-no-conflicting-release`, `cleanup-old-prereleases`, `scan-files-for-viruses`, `create-pre-release`, and JSON helpers such as `set-env-from-json`). That repo owns, documents and tests them; change them there, not here. They need no checkout. It runs `prepare` (tags `yyyy-mm-dd` / `yyyymmdd`, `BUILD-INFO.json`), then one `build-<platform>.yaml` per platform (only `build-darwin-arm64.yaml` for now; add Linux and Windows the same way), then `pre-release`. That last job scans for viruses, writes the release notes, keeps the 5 newest pre-releases, replaces an existing pre-release with the same tag (a stable one fails the run), and publishes.
- **macOS package**: a `.dmg` (drag Logix IDE to Applications), named `logix-darwin-arm64-<yyyymmdd>.dmg`. The build job runs `scripts/test.sh`, then `npm run tauri -- build --bundles dmg`, and checks the signature. The .dmg window (Logix IDE on the left, Applications on the right, 128 px icons, and a background with an arrow and "Install Logix IDE" and "Drag the Logix IDE icon onto the Applications folder.") is set in `bundle.macOS.dmg`. The background `src-tauri/icons/dmg-background.tiff` (1x and 2x) is drawn by `swift src-tauri/icons/make-dmg-background.swift src-tauri/icons/dmg-background.tiff`, whose positions must match that config; Tauri only applies it in CI because the step sets `TAURI_BUNDLER_DMG_IGNORE_CI=true`. The app is **ad-hoc signed** (`bundle.macOS.signingIdentity: "-"` in `tauri.conf.json`), since Apple Silicon requires a signature and the verify step checks for it. It isn't notarized, so the release notes tell users to clear the quarantine flag from the downloaded `.dmg` before opening it (`xattr -c ~/Downloads/logix-darwin-arm64-<yyyymmdd>.dmg`); the app dragged out of it is then not quarantined either.
- **The developer machine does only the minimal edit/run/debug cycle**: the dev server (`tauri dev`), unit tests, and lint/type checks. Don't add local scripts that produce installers, and don't make local development depend on signing setup.

## Architecture rules (keep the stack replaceable)

- **Thin IDE backend**: toolchain knowledge belongs in the engine (extended there if needed), not in the Rust layer.
- **One UI↔backend interface**: all UI-to-backend calls go through a single, documented set of Tauri commands and events (e.g. list boards, list/open examples, build, upload, stream output, report diagnostics, setup status). The UI must not run processes or touch the file system directly.
- **One engine adapter**: every engine call and every bit of knowledge about its results lives in `src-tauri/src/engine/`, so an engine change touches one place.
- **Console output**: tasks (`TaskEvent`s) and setup send lines through their own Tauri `Channel`; Auto Format's live output goes through `console_log` in `commands.rs` (`tool-output` events, a name kept from before the engine). Tool command lines are shown dimmed with `$`.
- **Framework-free core logic**: build folder preparation, examples, Bare Minimum and result mapping are plain code with unit tests and no dependency on Tauri or Svelte.
- **Behavior-level end-to-end tests**, in two halves, since Playwright can't drive the Tauri window on macOS (Tauri's WebDriver tool only supports Windows and Linux):
  - **UI**: `ui/e2e/*.e2e.ts` run the real UI in Playwright's WebKit (the engine behind the macOS window). `vite --mode e2e` (port 1430) replaces `ui/src/lib/backend.ts` with `ui/e2e/fakeBackend.ts`, which is typed against the real backend, so a changed backend API fails `npm run check` until the fake is updated. It uses the engine's real boards, Logix IDE's examples, and replays real engine output (`ui/e2e/fixtures/`); tasks also send a phase (`progress` events), and Upload's "Writing flash 42%"; a build fails if `main.v` contains "oops" or blinky's `;` after `assign led = counter[23]` is missing; tests trigger native-menu actions with `window.__fake.menu(id)`.
  - **Backend**: unit tests cover the engine adapter's parts (notification routing, result and error mapping, console), the examples and Bare Minimum; the `#[ignore]`d `real_engine_build` runs every task but Simulate against a real engine, and `real_examples_build` builds and tests every example and Bare Minimum (see Tests). `capture_fixtures` recaptures the fake backend's fixtures from a real engine.

## Source layout

- Top level (kept short for GitHub): `ui/` (the web UI project: `src/`, `e2e/`, `index.html`, `vite.config.ts`, `svelte.config.js`, `tsconfig.json`, the Playwright configs; builds to `ui/dist/`), `src-tauri/` (the Rust backend; Tauri's standard name), `scripts/` (`run.sh`, `test.sh`, `clean.sh`; they `cd` to the repo root), `docs/` + `mkdocs.yml`, and `package.json` / `package-lock.json`, which stay at the root because npm and the Tauri CLI run there. The npm scripts point Vite, Vitest, svelte-check and Playwright at the configs in `ui/` (Vite's `root` is `ui/`; Playwright's web server runs from the repo root, and test paths like `docs/images` are relative to it).

- `ui/src/`: Svelte 5 UI (runes syntax: `$state`, `$props`, etc.). Entry `main.ts` mounts `App.svelte`. Theme colors are CSS variables in `app.css`, with a dark-mode override.
- `ui/src/lib/backend.ts`: the UI↔backend interface. Every Tauri command used by the UI has a typed wrapper here; components never call `invoke` directly.
- `ui/src/lib/format.ts`: pure UI helpers (byte formatting, progress, capped console buffer), unit-tested in `*.test.ts` next to them.
- `src-tauri/src/commands.rs`: the Tauri commands (the backend side of that interface). New commands must also be registered in `lib.rs` (`generate_handler!`) and wrapped in `backend.ts`. Command structs use `#[serde(rename_all = "camelCase")]` to match TypeScript.
- Long-running commands stream progress to the UI with a Tauri `Channel` passed as a command argument (see `setup` and `backend.setup`). Shared backend state is `AppState` in `lib.rs`.
- `src-tauri/src/platform.rs`: the only place that identifies the OS/CPU (`Platform` enum, `is_implemented()`). Engine platform ids and exe name, the data dir, post-unpack fixups, opening folders and URLs, and bringing GTKWave to the front live here.

- `src-tauri/src/engine/`: the Logix Engine adapter, the only code that runs the engine or knows its layout. `mod.rs` has the pinned release and the data layout, `bundle.rs` downloads and unpacks the engine package, `client.rs` is the MCP session (`Engine::start`; `Engine::call` with optional progress, `call_with` also with live output and cancellation; a tool's error object comes back as `Err(value)`, not as a failed call). **rmcp handles each notification on its own spawned task**, so their order isn't kept and a call's result can arrive before its last notifications (lost console lines). So the IDE spawns the engine itself and its stdout goes through `tee`, which routes progress (by progress token) and `logix/output` (by `request_id`) synchronously, in order, before passing each line on to rmcp (`().serve((duplex, stdin))`); by the time a call has its result, it has had everything sent before it. **rmcp gives every request its own progress token and replaces any token the caller sets**, so `call` sends with `send_cancellable_request` and registers by the handle's `progress_token` and `id`; notifications that arrive before the call registers are kept and replayed in order (`Routes<K, T>`). `logix/output` is asked for with `_meta` `{"logix/output": true}` (`PeerRequestOptions.meta`). Cancel: `call_with` waits on `handle.rx` or the `CancellationToken`, then `handle.cancel()` sends `notifications/cancelled`; the engine stops its tools and, as MCP requires, never answers, so the call returns `{"category": "cancelled"}` itself. `catalog.rs` reads the boards (`get_catalog` with boards, FPGAs and families, `family` from the FPGA's `family`) and the project's own boards (`project_boards`: `get_catalog` with `custom_boards_file`, its `custom: true` boards; the engine's refusal comes back as `BoardsProblem`, with `console_lines`), `task.rs` runs the tasks (`Runner`: Verify, Upload, Run Tests, Simulate, Show Diagram), `format.rs` Auto Format, `devices.rs` the USB devices and connected boards, `setup.rs` the startup flow; `phase_sink` (`mod.rs`) follows the engine's phases. `info.rs` finds a package's program (`program_path`, from `get_engine_info`'s `bin_folder`). The result types the UI gets (`Task`, `TaskOutcome`, `TaskEvent`, `Diagnostic`, `BuildReport`, `dedup`) are in `src-tauri/src/outcome.rs`; `src-tauri/src/download.rs` downloads with progress and unpacks `.tgz`; the setup events are in `src-tauri/src/setup_events.rs`.

## Backend interface

All Tauri commands are in `commands.rs`, registered in `lib.rs` and wrapped in `ui/src/lib/backend.ts` (same names in camelCase). Failures reach the UI as `UserError { message, details }` (plain-language message, technical details).

- **App and setup**: `app_info` (name, version, platform, `platformSupported`); `setup` (sets up the engine; Channel of `SetupEvent`: stage `checking` / `downloadingEngine` / `downloadingEnginePackages` / `ready`, download bytes, engine download `progress` (`message`, `percent`), output lines, and `catalogReady`). Setup starts the engine (`engine::start_engine`), fills the board and example cache (`AppState.catalog`) and sends `catalogReady`, then lets the engine download its missing packages (`engine::download_missing`), so the start screen's Examples… and the board list work while the FPGA tools download (the user's request, 2026-11-10); the UI loads them on `catalogReady` (`loadCatalog`, once). Tasks still wait for `ready`. The running engine is kept in `AppState.engine`.
- **Catalog**: `get_boards` (`id`, `description`, `family`, `familyLabel`, `familyOrder`, `pinExtension`, `dimensions`, `configurations`, `custom`, `fpga`; the engine's boards), `get_examples` (`{ examples: [{ board, name, summary, notes }], hidden }`), `open_example(board, name)` (no tools needed), `open_bare_minimum(board)`.
- **Projects**: a project travels as `ProjectDoc { dir | null, templateDir | null, name, files: [{ name, text }], board | null, variant }`. Commands: `new_project(board?)` (the board's Bare Minimum), `last_board` and `last_variant` (for the start screen's toolbar), `recent_projects` (folders, newest first), `open_last_project`, `close_project` (forgets the last project), `open_project_dialog`, `open_project_at(dir)`, `save_project` (with removed files and the board and variant), `save_project_as_dialog`, `show_project_folder`, `copy_project_path`, `set_last_board(board, variant)`, `check_file_name(name, existing)` (error text or null), `set_last_board`.
- **Tasks**: `run_task(task, testbench?, key, sourceDir?, projectDir?, files, board, variant, device?, Channel of TaskEvent)` (`device`: Upload's chosen device id, null to use the only one that fits) with task `build` / `upload` / `test` / `simulate` / `graph`; a `TaskEvent` is `{ kind: line, line, tool?, redraw? }` (`tool` for a tool's own lines, `redraw` when the tool prints over it) or `{ kind: progress, message, percent? }`. It returns `TaskOutcome { ok, diagnostics, testbenches: [{ name, passed }], report, cancelled, graphSvg, seconds, action?, devices }` (`action`: the engine's suggested action code on failure, e.g. `connect_board`, or `select_device` with the candidates in `devices`). A diagnostic is `{ severity: error | warning, file?, line?, column?, message }`; the report `{ arch, resources: [{ name, used, available }], clocks: [{ name, fmaxMhz }] }`. Also `cancel_task`, `format_file(name, text)` (`{ ok, text?, diagnostics }`), `save_gtkwave_layouts(key, projectDir)`.
- **Devices**: `scan_devices` (`{ usb: [{ id, vid, pid, manufacturer, product, serialNumber, boards: [{ board, level }], buildMatch }], unreachable: [{ vid, pid, action, actionDescription }] }`), `connected_devices` (`[{ id, name, serial, boards: [{ board, level, variants }] }]`).
- **Language server**: `lsp_start`, `lsp_send`, `lsp_stop`; events `lsp-message`, `lsp-closed`.
- **Settings**: `get_preferences`, `set_preferences` (returns the stored values), `choose_folder_dialog`.
- **Window**: `ask_confirm(title, message, ok_label, kind?)`, `ask_save_changes` (`save` / `discard` / `cancel`), `set_document_state(name, dirty)` (an empty name: no project, title "Logix IDE"), `close_window`, `show_editor_menu` (its items follow the menu state), `set_menu_state(menu)` (`{ project, verilog, comment, definition, testbenches, simulate, testbenchOpen, variantMenus }`), `show_output_menu`, `log_output(lines)`.
- **Events** to the UI: `menu`, `open-recent`, `tool-output`, `close-requested`, `lsp-message`, `lsp-closed`.

## Files Logix IDE writes

- **`logix-ide.toml`** (in the project): `board = "<board id>"`, after a first line `# Logix IDE project settings.` in new files, and for a board variant that isn't the default a `[variant]` table (e.g. `memory = "ram"`). **Decided** (with reasons): named for the IDE, since each Open Logix frontend owns its project model (a shared `logix.*` could collide with other frontends' files); TOML because it allows comments, and Logix IDE edits it with `toml_edit`, which changes only its own values and keeps the user's comments, layout and other settings (JSONC would make that harder). Projects from before (with `logix.json`) aren't supported (the user's decision: pre-release).
- **`~/.logix/ide/`** (decided 2026-11-10: every Open Logix program has its own folder in `~/.logix`, on every OS, and the IDE writes `~/.logix/README.txt`, saying what each is, when it's missing; `platform::data_dir_from`, `write_logix_readme`): `engine-release/` (the unpacked engine package plus `download-metadata.json` with its source URL; a different pinned URL triggers a re-download), `engine/` (the engine folder, owned by the engine: packages, logs, scratch), `dev/engine/` (the engine folder of a local engine, `LOGIX_DEV_ENGINE_BINARY`), `_scratch/` (temporary: `engine-download/` for the engine package, `build/` for Verify etc., with the engine's output in `_build/`, `example/` for the last opened example, `format/` for Auto Format), `logs/`, and `settings.json`: `lastProject`, `recentProjects`, `lastBoard`, `lastVariant` (only when not the default), `recentBoards` (the board picker's "Recently used", newest first, up to 5), `projectsDir`, `editorFontSize` (default 13, 8 to 32), `uiScale` (percent, 50 to 300; unset means automatic), `theme`, `lintOnVerify`, `liveChecking`, `hoverInfo`, `showOutput` (`onCommand` default, `onError`, `never`).
- **Empty `main.v`** (`examples::EMPTY_MAIN`, for boards without a Bare Minimum): a comment that the top module must be named `main` and how to add ports and a pin file, then `module main;` with "Your design goes here."; it builds as is.
- **`boards/`** (in the project, only if the user adds it, with another editor): the project's own boards, a file per board; Logix IDE never writes them (see The project's own boards).
- Reserved names that are never project files: `logix-ide.toml` and `_build`.

## CI and release workflows

Use the current major versions of GitHub's actions (`actions/checkout`, `setup-node` with `lts/*`, `upload-artifact`, `download-artifact`, `setup-python`, `upload-pages-artifact`, `deploy-pages`), `dtolnay/rust-toolchain@stable` with `clippy, rustfmt`.

- **`test.yaml`**: on every push and pull request, manually, and daily at 00:00 UTC; a newer run for the same ref cancels the older one; matrix macos-15, macos-26, macos-latest with `fail-fast: false`, 30 min. Steps: checkout, Node (npm cache), Rust, `npm ci`, `npx playwright install webkit`, `scripts/test.sh`.
- **`build-pre-release.yaml`**, three jobs:
  - `prepare` (Ubuntu): release tag `yyyy-mm-dd` and package tag `yyyymmdd`; an early check that no stable release has that tag; repo `owner/repo` (lowercase, from the `origin` URL), branch and full commit; the version from `tauri.conf.json`. Writes `BUILD-INFO.json` (`package-name` logix, `description` (the motto), `logix-version`, `repo`, `repo-branch`, `repo-commit`, `release-tag`, `package-tag`, `build-time`, `builder-workflow`, `workflow-run-id`, `workflow-run-number`), formatted, as the `build-info` artifact.
  - `build-darwin-arm64` (reusable workflow, `macos-latest`, 60 min): checks it runs on darwin/arm64, adds `target-platform` to the build info, checks out exactly `repo-commit` into `_repo/` (so every platform builds the same commit), sets up Node and Rust, `npm ci`, installs WebKit, runs `scripts/test.sh`, builds the .dmg, requires exactly one and names it `logix-darwin-arm64-<package tag>.dmg`. Then it checks the .dmg: `hdiutil verify`, mounts it, finds the `Applications` link and `.DS_Store`, and `codesign --verify --deep --strict` plus "Signature=adhoc" on `Logix IDE.app`. Artifact `logix-darwin-arm64`.
  - `pre-release` (Ubuntu): downloads all artifacts into `_artifacts/`, scans the .dmg files with ClamAV, makes `build-info.txt` (aligned `key : value`), an installers table (system, architecture, installer type, link), a run summary (build info, commit link, release link), and the release notes: the motto in bold, then links to the product page and the docs; macOS install steps (download to Downloads, the `xattr -c` command and why, drag to Applications, the first start downloads the FPGA tools and may take a few minutes); uninstalling (drag to the Trash; `~/.logix/ide` holds the tools and settings, not projects); the installers table; the build info; and "About these releases" (daily pre-releases, about 5 kept, made stable by changing the status from Pre-release to None). Then it deletes all but the 5 newest pre-releases, deletes a pre-release with today's tag, and creates the pre-release (name = tag) with the .dmg and `BUILD-INFO.json` listed by exact name, so a missing file fails the run.
- **Actions**: the shared ones in `openlogix/.github` (see that repo's `CLAUDE.md` for each action's inputs and behavior). Jobs check out this repo only when a step needs its files (`prepare` for `get-repo-info`, the build job's `_repo/`).
- **`publish-docs.yaml`**: Ubuntu, Python 3.14, `pip install -r docs/requirements.txt`, `mkdocs build --strict` into `_site/`, then `upload-pages-artifact` and `deploy-pages` (permissions `pages: write`, `id-token: write`; environment `github-pages`). The repo's Pages source must be set to GitHub Actions.
- **Open Recent / Show Project Folder**: `settings.json` keeps up to 10 recent project folders (`recentProjects`, newest first), updated whenever a project is opened or saved. `menu::refresh` rebuilds the menu bar so File > Open Recent stays current; its items are `recent:<index>`, emitted to the UI as `open-recent` with the folder, then `open_project_at` loads it (a folder that can't be loaded is dropped from the list). Project > Show Project Folder (Option+Cmd+K, as in Arduino) opens the folder via `Platform::reveal_folder` (`open` on macOS). For a project never saved (no folder), it asks first with an info `ask_confirm` ("This project hasn't been saved yet", button "Save As…"), then saves and shows the new folder: a status line alone was easy to miss. Opening Terminal in the folder was tried and dropped: a `cd` in the user's shell startup files moves the shell away. `ask_confirm` takes an optional `kind`, `info` or (default) `warning` for destructive actions.
- **Stop** (toolbar button, always shown and greyed out while nothing runs; Project > Stop, Cmd+.): `cancel_task` triggers the `CancellationToken` the running `run_task` holds (`AppState.task_cancel`). The engine call then sends MCP's cancel and the engine stops its tools (see the engine adapter). A stopped Verify skips its remaining steps; the status says "Build stopped."
- **Editor right-click menu** (as in Arduino IDE 2, shorter): Go to Definition (F12), Cut/Copy/Paste/Select All, Comment/Uncomment (Cmd+/), Auto Format; greyed out as in the menu bar (see Items only when they can be used). Nothing is selected when it opens, not even a board's only example (the user's decision: changing the board, especially to another FPGA or family, must be a choice, not a default); the main button reads "Choose an Option", disabled, until one is, and Enter does nothing. It has no search field (few choices; the user's decision). Section headings ("Current project", "Recent projects", "New project") use the board picker's group heading band (`--group-bg`, `--group-fg`) so they stand out from the entries. Cancel, Esc and ✕ cancel the board change (`closeExamples(false)`). In this dialog the selection's green background (the app's convention) covers only the choice's title, a band across the row, so its note below stays readable (the user's request); a recent project, one line, is filled whole. The dialog ignores keys until after the event that opened it (`armed`): the Enter that picks a board in the board list reached it and applied the default choice at once. Opening an example or project brings its own board, so "Save changes?" is only asked about real edits.
- **Board picker** (`ui/src/lib/BoardPicker.svelte`, like Arduino IDE 2's board selector; replaced a native `<select>`, which can't report picking the current board): a button with the board's name opens a searchable list (combobox + listbox, arrows/Page/Enter/Esc), "Recently used" first (the boards picked most recently, newest first, up to 5: `recentBoards` in `settings.json`, updated by `set_last_board`, which returns them, and read by `recent_boards`; the user's request, 2026-11-06: it isn't based on guesses, unlike the dropped connected-device groups), then all boards grouped by FPGA family (`Board.family` from the engine catalog's FPGA `family`, with its `familyLabel` and `familyOrder` from the catalog's `families`, such as "Lattice iCE40" first, then "Lattice ECP5", "Gowin GW1N" and so on; families the engine doesn't describe come last, by ID; `groupByFamily` in `ui/src/lib/boards.ts`). Each entry's hover hint names its FPGA ("FPGA: Lattice iCE40 ICE40HX4K-TQ144 (8k)", `fpgaLabel`), and the search also matches the FPGA's part number and ID, though they aren't shown (the user's request, 2026-11-06: to find a board like theirs). Picking any board, the current one included, calls `setBoard`. The selected board is marked with a small accent-colored dot, not a check mark, which looked like the groups' arrows (the user's request). Group headings use their own theme colors, `--group-bg` and `--group-fg` in `ui/src/app.css` (a gray a little darker than the list, light and dark: the user preferred gray to the earlier teal tint), so they stand apart from the entries, and long titles wrap left aligned with the count on the right (the user's request). "Recently used" is collapsible too: it starts expanded, and its collapsed state is kept only in memory (`recentCollapsed`). The project's own boards (the boards folder) come first, in "Custom boards" (the user's design and naming, 2026-11-07: "custom", not "project's", since the project's catalog board is a project board too; `CUSTOM_GROUP`, `kind: "custom"` in `boardGroups`; it starts expanded and its collapsed state is kept only in memory, like "Recently used"), and also first in their family's group, with the board icon and tooltip; never in "Recently used" (other projects don't have them). A boards folder with problems keeps the group, empty (count 0), with the quiet problem line inside it. FPGA family groups are collapsible in the picker and in the Examples dialog's boards column (`groupByFamily`); the expanded ones are shared by both and remembered in `localStorage` (`ui/src/lib/expandedGroups.svelte.ts`, all collapsed by default), opening a list expands the current board's group, and a search shows matches in all groups.
- **Board**: chosen in the toolbar's board picker and stored in `logix-ide.toml`. Changing it offers the board's examples (see New projects) and, if the files are kept, marks the project as unsaved.
- `src-tauri/src/menu.rs`: native menu bar. New/Open/Save/Save As are emitted to the UI as `menu` events; Close and Quit go through the window-close flow. File dialogs and the "Save changes?" prompt run in Rust (`tauri-plugin-dialog`), so the UI needs no dialog or file system permissions.
- **Closing with unsaved changes**: the UI reports the dirty flag with `set_document_state`. When it's set, `CloseRequested` is blocked and a `close-requested` event goes to the UI, which asks Save / Don't Save / Cancel and then calls `close_window`.
- `src-tauri/tauri.conf.json`: app name/identifier, window, dev server port (1420, must match `ui/vite.config.ts`), bundle settings.
- `src-tauri/capabilities/`: Tauri permissions granted to the UI. Keep them minimal; prefer adding Rust commands over granting the UI file system or shell access.
- `src-tauri/icons/`: app icons, generated from `icon-source.png` with `npx tauri icon src-tauri/icons/icon-source.png` (delete the generated `android/` and `ios/` folders). The source is the Open Logix brand icon for Logix IDE (org site `docs/brand/ide.svg`: a `#10B981` to `#0F766E` diagonal gradient tile with rx 16 of 64, and a white window (rect 14,17 36x30 rx 6, stroke 4.5) with a filled play triangle), drawn by `swift src-tauri/icons/make-icon-source.swift src-tauri/icons/icon-source.png`; keep it equal to the brand icon (also used as the docs logo). The 64-unit drawing is scaled to about 824 px and centered on a transparent 1024 px canvas, Apple's icon size; a full-bleed square looks oversized in the Dock next to other apps.

## Development notes

- **Testing first-run setup** without touching the real `~/.logix/ide`: run with `LOGIX_IDE_HOME=<tmp folder>` (or a temporary `HOME`, keeping `CARGO_HOME`/`RUSTUP_HOME` pointing at the real ones). Symlink `<tmp folder>/engine` to an existing engine folder to avoid re-downloading about 650 MB of packages.
- **Environment variables** (the Open Logix naming scheme, website repo's `CLAUDE.md`): `LOGIX_DEV_ENGINE_BINARY` (runtime, the shared convention; see Dev engine); `LOGIX_IDE_HOME` (runtime, for testing: an absolute path used instead of `~/.logix/ide/` for everything the IDE keeps there, settings and recent projects included, so a test can start the IDE on settings and projects it generated; a relative path is an error, never a silent fallback; logged at startup; `platform::data_dir_from`); build: `LOGIX_IDE_BUILD_VERSION` (pre-release workflow), `LOGIX_IDE_BUILD_ENGINE_REPO` / `LOGIX_IDE_BUILD_ENGINE_TAG` (set by `src-tauri/build.rs` from the pinned engine, read by `engine/mod.rs`); tests: `LOGIX_IDE_TEST_ENGINE_FOLDER`, `LOGIX_IDE_TEST_VERIBLE_LS`, `LOGIX_IDE_TEST_FIXTURES_OUT` (ignored real-engine tests and fixture capture).
- **Log**: backend messages go through `log!(...)` (`src-tauri/src/logging.rs`), which prints `[logix] ...` to the dev terminal and appends it with a UTC time to `~/.logix/ide/logs/logix.log` (one file per run, the last 5 kept as `logix.1.log`...), since an app opened from Finder has no visible stderr. It logs the startup header (versions), every error returned to the UI (`From<anyhow::Error> for UserError`), crashes (panic hook), the existing status lines (setup, language server, GTKWave), and every output pane line as `| <line>` (`log()` in `App.svelte` batches them to `log_output`; colors removed; above 10 MB per file only messages are kept). Help > Show Log Folder opens it; Help > Report a Problem pre-fills the issue text asking for `logix.log`. Use `log!` instead of `eprintln!`. There's no way to see the window from automation, so ask the user to confirm UI changes visually.
